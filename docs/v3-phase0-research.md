## 0. 結論サマリ

### 推奨案

1. **画面構成は「背景＋立ち絵＋少数の一枚絵」の 3 層**（ベル案を支持）。ただし 1 点修正する。「姿勢が固定される場面」のうち *膝を抱えて座るリーネ* は本文に 3 回出てくる（`meet`／`night`／`boss` の影）。ここは一枚絵 CG ではなく **透過の「座りポーズ立ち絵」1 系統**にまとめると、3 場面を 1 つの素材系統で賄え、`boss` の影は同じ絵をシルエット化するだけで本文（「初めて出会ったときの、リーネと同じ姿に」）と絵が一致する。
2. **データ形式はベル案（`text` 配列に文字列とオブジェクトの混在を許す）を採用**。理由は、全 20 シーン中 11 シーンの `text` が state を受け取る関数で、段落が条件で増減するため、本文と演出を別ファイルに分けると対応がずれるから。本文の文字列は 1 文字も動かさず、演出指定を同じ要素に「添える」だけにする。
3. **セーブ互換は保てる**。セーブデータが持つのはシーン ID・数値・フラグ・バックログ（文字列配列）だけで、ページ位置や画像の情報は持っていない［実測］。守るべき条件は 1 つ：**バックログに入れる `paras` を文字列配列のままにする**こと（§A-4）。
4. **光輪は絵に描き込まず、SVG/CSS の別レイヤー**にする。位置（胸か背か）・形（歯車／砕けた時計／懐中時計と現状 3 種）・明滅・消失（TRUE END）のすべてをコードで制御でき、生成のばらつきと背景除去の失敗要因（発光・半透明）を同時に消せる。
5. **不一致監査の結果**：21 枚中、本文と明確に矛盾するもの 4 枚（`meet`／`explain`／`boss`／`end_true`）、重要要素の欠落・場所違い 7 枚、軽微 9 枚、問題なし 1 枚（§B）。新規に必要な背景は最小 4 枚で、**10 枚は無人背景としてそのまま流用できる**。
6. **スマホ縦は「立ち絵分離」で大半が解決する**。縦持ち（390×844）では 16:9 背景の**横幅の中央約 26% しか見えない**［実測・計算］。人物を背景に焼き込む限りこの問題は消えないが、立ち絵は画面基準で置くので切れない。背景側は既存の `position` 項目（マニフェストに実装済み・現在未使用）で焦点を合わせる。
7. **Phase 1 は `meet`＋`explain` の縦切り試作**。ここで「キャラ一貫性」と「座りポーズの接地」の 2 つに合否を付け、通らなければ Phase 2 の前に方式を切り替える。

### 最大のリスク

**キャラクター（リーネ）の一貫性**。現行の 3 枚（`title`／`meet`／`end_true`）ですら衣装・髪飾り・瞳の色・光輪の形がすべて違う［実測］。立ち絵 7〜10 表情＋座りポーズ＋CG を同一人物として揃えるには、文章指定や seed 固定だけでは足りない可能性が高い。対策は段階式（§D-2）：まず「基準絵 1 枚＋顔領域だけの描き直し」で表情差分を作り（体は画素単位で同一になる）、姿勢の違う絵で崩れるならキャラ LoRA の学習に進む。Anima の inpaint／参照系の成熟度は今回確認しきれておらず［未確認］、Phase 1 の最初の検証項目とする。

次点のリスクは **座りポーズ立ち絵と背景の接地ずれ**（画面比で背景の切り出し位置が変わるため、石段と尻の位置が合わなくなる。§A-6・§E-4）。

### A-3. データ形式の候補比較と推奨

| 案 | 概要 | 長所 | 短所 | 評価 |
| --- | --- | --- | --- | --- |
| **① 混在配列**（ベル案） | `text` の要素を「文字列 または `{ text, speaker, ... }`」にする | 本文と演出が同じ場所にあり、条件分岐で段落が増減してもずれない。未指定の段落は今のまま動く。移行を 1 シーンずつ進められる | `story.js` に演出指定が混ざり、ファイルが長くなる | **推奨** |
| ② 演出の別表 | 本文は触らず、`stage.js` 等に「シーン ID＋段落番号 → 演出」を持つ | `story.js` の差分がゼロで、本文不変の証明が自明 | 11 シーンは段落数が可変なので、番号がずれる。本文の一部をキーにする方法も、同一文が複数ある（「歯車が回る。カチリ、と…」は 2 エンディングに登場）ため壊れやすい | 不採用 |
| ③ 文字列内タグ | `"@rine:smile 「…」"` のように本文へ記号を埋める（TyranoScript 風） | 記述が短い | 本文の文字列そのものが変わる。バックログ・既読・検証のすべてでタグ除去が要る。「本文改変禁止」の確認が難しくなる | 不採用 |
| ④ 命令列スクリプト | `[{show}, {say}, {fx}, ...]` の命令列に全面移行（Ren'Py 風） | 表現力は最大 | 99 段落の作品には過剰。全シーン書き直しでリスクが大きい | 不採用 |

**推奨スキーマ（①の具体形）**

```js
// js/story.js（イメージ。Phase 0 では実装しない）
cast: {
  rine:   { name: "リーネ", color: "#f2d48a" },
  girl:   { name: "少女",   color: "#f2d48a", chara: "rine" }, // 名乗る前の表示名
  shadow: { name: "影",     color: "#b9a4e6" },
  shard:  { name: "欠片の声", color: "#ffffff" }
},

scenes: {
  meet: {
    stage: { bg: "tower_foot" },          // シーン開始時の舞台（省略時は従来どおりマニフェストの image）
    text: function (s) {
      var t = [];
      if (s.flags.petal) t.push("指先が触れた瞬間、…");            // 文字列のまま＝地の文・演出なし
      t.push(
        { text: "時計塔の足元。苔むした石段に、…座っていた。",
          chara: "rine", pose: "sit", expr: "down", pos: "center" },
        "淡い金色の髪。星を閉じ込めたような瞳。…",
        "この止まった世界で、…初めてだった。",
        { text: "少女はゆっくり顔を上げ、目を見開いた。「……動いてる。…」",
          speaker: "girl", expr: "surprised", fx: "hop" }
      );
      return t;
    }
  }
}
```

各項目（すべて省略可。`text` だけ必須）：

| 項目 | 意味 | 備考 |
| --- | --- | --- |
| `text` | 本文。**現行の文字列をそのまま入れる** | 検証スクリプトで v2.1 と完全一致を確認（§A-5） |
| `speaker` | 話者 ID（`cast` のキー）。省略＝地の文 | 名前札と色に使う。`cast[x].chara` で立ち絵の人物に対応付け |
| `chara` / `pose` / `expr` / `pos` | 1 人ぶんの立ち絵指定の省略記法 | `speaker` があり `chara` が無ければ、話者の立ち絵に適用 |
| `show` | 複数人をまとめて指定：`[{ chara, pose, expr, pos }]` | 2 人以上を同時に動かすときだけ使う |
| `hide` | 退場させる人物 ID の配列。`"*"` で全員 | |
| `bg` / `cg` | このページから背景・一枚絵を切り替える | シーン途中で絵を変える用途 |
| `halo` | 光輪の状態：`"weak" / "flicker" / "bright" / "off"` | §A-7 |
| `fx` | このページに入った瞬間の演出。文字列または配列 | 既存のシーン単位 `enter` はそのまま残す |

設計上の約束：

- **状態は持ち越す**。一度出した立ち絵・表情は、変更か退場の指定があるまで続く。シーンをまたぐときは `stage` の指定で初期化する。
- **状態は純関数で求める**。`stageAt(pages, index)` が 0 ページ目から index まで畳み込んで「いま誰がどの表情でどこにいるか」を返す。スキップ・ロード・バックログから戻ったときも同じ結果になる（A-2 の #5 への対処）。
- **論理名とファイル名を分ける**。`story.js` は `rine / surprised / tower_foot` といった論理名だけを書き、ファイルへの対応は `assets/manifest.json` 側で持つ。これで「ファイルが無くても止まらない」という現行の性質を保てる。

**マニフェストの拡張（version 2 のイメージ）**

```json
{
  "version": 2,
  "backgrounds": {
    "tower_foot": { "image": "images/bg/tower_foot.webp", "position": "50% 40%", "positionPortrait": "50% 45%" }
  },
  "characters": {
    "rine": {
      "base": "images/chara/rine/",
      "poses": {
        "stand": { "body": "stand.webp", "exprs": { "normal": "stand_normal.webp", "surprised": "stand_surprised.webp" },
                   "halo": { "x": 50, "y": 22, "size": 46 } },
        "sit":   { "exprs": { "down": "sit_down.webp", "surprised": "sit_surprised.webp" },
                   "halo": { "x": 52, "y": 30, "size": 40 } }
```

`scenes[id].image` は残す。`stage.bg` が無い・読めないシーンは従来の 1 枚絵で動くので、移行途中でも全シーンが遊べる状態を保てる。

**混在段落（29 件）の扱い**：本作は地の文と台詞が 1 段落に同居する文体なので、段落を分割して話者を付けることはしない（ページ割りが変わり、本文改変に近づく）。名前札は `speaker` を指定した段落にだけ出し、地の文主体の段落では出さない。台詞部分（「…」）だけを話者色にする装飾は Phase 2 の任意項目とする。

### A-4. セーブ互換の根拠［実測］

| キー | 中身 | v3 での扱い | 互換の根拠 |
| --- | --- | --- | --- |
| `chrono-tale-save-v1` | `{scene, affection, shards, flags, steps, log}` | 形を変えない | `isValidSave()` が見るのは `scene` の存在・非エンディング、数値 2 つ、`flags`。シーン ID を変えなければ旧データは有効。ページ位置・画像情報は元々入っていない |
| `chrono-tale-slots-v1` | `{ "1": {savedAt, state}, ... }` | 形を変えない | 同上 |
| `chrono-tale-endings-v1` | エンディング ID の配列 | 変えない | エンディング ID（`true/normal/bad/another`）を変えない |
| `chrono-tale-read-v1` | シーン ID の配列 | 変えない | シーン単位の既読のまま使う |
| `chrono-tale-settings-v1` | `{textSpeed, skipRead, volume, muted, images}` | **項目を足すだけ** | `loadSettings()` は項目ごとに既定値で補うので、旧データに新項目が無くても動く。逆に v2.1 へ戻しても、知らない項目は無視される |

守るべき条件：

1. **シーン ID 20 個とフラグ名を変えない**。
2. **`state.log` の `paras` は文字列配列のまま保存する**。オブジェクトを入れると、(a) 旧データと新データで形が混在し、(b) 万一 v2.1 に切り戻したときにバックログが `[object Object]` になる。話者名をログに出したい場合は、`paras` と同じ長さの別配列（例 `who: ["", "", "", "少女"]`）を足す。旧版はこれを無視するだけで壊れない。
3. **`restoreState()` の補完方式を踏襲**する（無い項目は既定値で埋める）。

未決事項：**文単位の既読**（既読の行だけ色を変える等）を入れるなら、シーン単位の現行キーでは表現できない。現行キーの変更は禁止なので、やるなら新しいキーの追加になる。これはマスター判断とし、推奨は「v3.0 ではシーン単位のまま」（§E-6）。

### A-5. 移行手順（本文不変を機械的に証明する）

1. **基準の採取**：v2.1 の `story.js` を Node で読み、フラグ 12 個の全組合せ（4,096 通り）× 20 シーンで `text` を展開し、文字列の並びを JSON に保存する。今回の調査でも同じ方法で段落統計を取れることを確認済み。
2. **正規化層の追加**：`normalizePage(p)`（文字列なら `{ text: p }` に包む）を入れ、ページ送り・ログ・文字送りはすべて正規化後の値を使う。この時点で `story.js` は無変更、見た目も無変更。
3. **1 シーンずつ変換**：文字列をオブジェクトに置き換えるたびに、手順 1 と同じ展開をして `text` だけを取り出し、基準 JSON と**完全一致**することを確認する。差分が 1 文字でも出たら失敗とする。
4. **`choices` は触らない**。選択肢の文・効果・遷移は今回の範囲外。
5. **版の更新**：`VERSION`、`data-app-version`、`?v=` を揃えて 3.0 に上げる（最後に 1 回だけ）。

### A-6. 名前札と複数キャラ表示の設計

**名前札（話者の色分け）**

- 現在の `#scene-title`（シーン名）は、右隣の `#scene-step`（「第 2 幕」）側へ寄せて「第 2 幕　時計塔の少女」とし、名前札の位置は話者名に明け渡す。シーン名は入場時のバナーにも出ているので情報は減らない。
- 地の文のページでは名前札を隠す（枠ごと消すとウィンドウの高さが変わるので、高さは保ったまま透明にする）。
- 色は `cast[x].color` を CSS 変数 `--speaker` に流し、名前札の文字色と下線に使う。**色だけに頼らず、必ず名前を文字で出す**。ウィンドウ地色に対してコントラスト比 4.5:1 以上を確認する。
- 名乗る前の表示名に対応する：`meet` の台詞は「少女」、`explain` 第 1 段落以降は「リーネ」。`cast.girl` のように別 ID を立て、立ち絵は同じ人物を指す。
- 話者の一覧（本文から抽出）：リーネ／（名乗る前の）少女／影（時喰いの王）／〈真昼の欠片〉の声／古文書（『』書き）／水鏡の中の自分（『』書き）。主人公の発言は選択肢にしか現れない。
- フォーカス先とスクリーンリーダー向けの見出しは維持する（シーン名の `<h2>` を残し、話者名は別要素にする）。

**複数キャラ表示と話者強調**

- `#char-img` 1 個を、人物ごとの枠 `.chara[data-id][data-pos]` に置き換える。枠の中は下から「光輪 → 体 → 顔差分」の重ね。
- **同時に画面に出る人物は最大 2 人で足りる**。本文上、リーネと同時に立つのは影（`boss`／`sacrifice`／`end_still`）と時喰いの獣（`forest`）だけ。主人公は一人称で画面に出ない。村の少女・パン屋の主人・渡し守は「止まった人」なので背景側の存在として扱う。
- 話者強調：話者は明るさ 100%・手前、非話者は明るさ 60% 前後（TyranoScript の `talk_focus` 既定値と同じ水準［外部］）。地の文のページでは全員を通常の明るさに戻す。
- 位置は `left / center / right` の 3 つを維持し、**縦画面では別の値を使う**：2 人のときは縮尺を約 75% に落として 32%／68% に寄せる。1 人のときは常に中央。
- **縦横の基準の持ち方**：立ち絵の横位置は画面基準、縦位置と大きさは背景基準、という二本立てを Phase 1 で試す。画面比が変わると背景の切り出し位置が動くため、画面基準だけで置くと「石段に座る」絵で接地がずれる（最大リスクの次点）。

### A-7. 光輪の別レイヤー設計

- **SVG/CSS で描く**（生成しない）。「砕けた文字盤のような光の輪」＝欠けのある円環＋時刻の目盛り＋ひび。1 つの SVG を全場面で使うので、形が場面ごとに変わる問題が原理的に起きない。
- 立ち絵の**背面**に置く（体より下のレイヤー）。位置はポーズごとにマニフェストの `halo: { x, y, size }`（立ち絵枠に対する %）で持つ。
- 状態：`weak`（既定、弱い明滅）／`flicker`（`explain` 末尾「また弱々しく瞬いた」）／`bright`（`sacrifice` の光）／`off`（`end_true`「光輪の消えたリーネ」）。
- 一枚絵 CG では背面に差し込めないので、CG には光輪を描き込まない構図（背中が見えない角度）か、CG の上に重ねて違和感が無い位置に限る。これも「座りポーズは透過立ち絵にする」理由の 1 つ。
- `prefers-reduced-motion` では明滅を止め、弱い発光の静止状態にする。

### D-1. 背景：MOSS と Anima の A/B 試作計画

前提として確認できたこと［外部］：

- **Anima**：CircleStone Labs と Comfy Org による 2B パラメータのアニメ系テキスト→画像モデル（NVIDIA Cosmos-Predict2 ベース）。ComfyUI が標準対応。Base／Aesthetic／Turbo の変種がある。重みのライセンスは非商用ライセンスで、生成物の扱いはモデルカードの現行文面を要確認。現行 21 枚は Anima 製（コミット履歴）。
- **MOSS-Image**：5B パラメータのオープンウェイトモデル。Apache 2.0。ComfyUI 0.42.0 以降が必要。**枠を描いて配置を指定する領域誘導生成**が特徴。第三者の検証では写実表現は強いが、配置や文字の制御は安定しないという評価がある。アニメ調背景の品質についての第三者評価は見つからなかった。

| 項目 | 内容 |
| --- | --- |
| 題材 | 新規に必要な 3 場所：塔の足元・石段／村の広場／砂丘の夜 |
| 条件 | 2 モデル × 3 場所 × 各 4 枚 ＝ 24 枚。指示文は本文の事実チェックリストから作り、両モデルで同じ内容にする |
| 評価 1：本文適合 | チェックリストの合致数（例：塔の足元＝苔・石段・草原・街が無い・人がいない・窓に灯りが無い） |

### D-2. キャラクター一貫性対策の比較

| 方式 | 内容 | 一貫性 | 手間 | 適する対象 | 懸念 |
| --- | --- | --- | --- | --- | --- |

| ⑤ 参照画像方式 | 基準絵を参照入力にして別の絵を作る | 中〜高 | 中 | 一枚絵 CG | Anima／MOSS での対応状況が未確認 |

**推奨（段階式）**：

1. ①で基準絵（立ち・正面寄り・無表情・単色背景・光輪なし）を 40〜80 枚生成し、1 枚に確定する。**ここがマスターの確認ポイント**。
2. ③で表情差分を作る（描き直した顔領域だけを元の絵に貼り戻し、体を画素単位で同一に保つ）。③が使えなければ②で代替。
3. 座りポーズで同一人物に見えなければ、④へ進む。
4. 一枚絵 CG は④または⑤で作る。

**合否基準（Phase 1）**：基準絵と表情差分 3 枚を並べ、(a) 体の輪郭が画素単位で一致、(b) 衣装の金の縁取りと帯の形が同じ、(c) 瞳の色と髪色が同じ、(d) 第三者（マスター）が見て同一人物と即答できる。座りポーズは (b)〜(d) を満たすこと。

### D-3. 表情編集・光輪・透過処理

**表情（顔領域の描き直し）**

- 対象領域は眉・目・口を含む顔の内側。前髪にかかる部分は領域に含めすぎない（髪が変わると別人に見える）。
- 変化量は小さめに。大きくすると顔の造形ごと変わる。
- 仕上げで必ず「描き直した領域だけ」を元絵に合成する。全体を再エンコードした絵をそのまま使うと、体の画素がわずかに変わり、切替時にちらつく。
- 実装側は、当面「表情ごとに全身 1 枚」で持つ（現行の `<img>` 1 枚の延長で済む）。容量が問題になれば、体 1 枚＋顔の小片に分ける。

**光輪**

- §A-7 のとおり SVG/CSS で描き、生成しない。立ち絵・座りポーズの生成指示には「光輪なし・発光体なし」を明記する。
- 代替案（生成した光輪画像を別ファイルで重ねる）は、SVG の見た目が画風に合わなかった場合の予備とする。

**透過処理の比較**

| 方式 | 内容 | 長所 | リスク |
| --- | --- | --- | --- |
| **(a) 単色背景で生成→背景除去** | 単色背景で人物を生成し、背景除去モデルで切り抜く | 生成モデルを選ばない（Anima のまま可）。道具が揃っている | **髪の縁に背景色が残る**。細い毛先・指が欠ける。半透明や発光が失われる。**白い衣装＋淡い金髪は、白背景でも緑背景でも切り抜きにくい組み合わせ** |
| (b) 透過つきで直接生成 | 透過情報を持つ画像を直接生成する拡張を使う | 髪の縁や半透明がきれい | 対応モデルが限られる。Anima／MOSS での対応は確認できていない。別モデルを使うと画風が変わる |

推奨は (a)。リスクへの手当て：

- 背景色は**中間の灰色**（例 `#808080`）を第一候補にする。白衣装とも淡い金髪とも明度差があり、縁に色が残っても緑ほど目立たない。
- 背景除去は、アニメ絵向けに調整されたモデルを使う。BiRefNet をアニメ絵 1,228 枚で追加学習した ToonOut は、著者の評価で画素精度 95.3%→99.5% と報告されている（MIT ライセンス）［外部］。髪の毛先・指が誤りやすい箇所であることも同論文が指摘している。
- 切り抜き後に、縁の色抜きと 1px の収縮をかけ、**暗い背景（`campfire`）と明るい背景（`river`）の両方に重ねて**縁を目視確認する。
- 現行 CSS は立ち絵に `drop-shadow` を掛けているため、縁の乱れが影として強調される。検証は必ず実機表示で行う。
- 光輪を別レイヤーにしたことで、切り抜きが最も苦手な「発光・半透明」が立ち絵から無くなる。
