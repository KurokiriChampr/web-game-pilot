## 1. 設計の判断

### 1-1. 宣言の置き場所：`STORY.unlocks`（`WORK` ではなく `STORY`）

```js
var STORY = {
  unlocks: {
    seen_aoi:   { endings: ["bad_aoi"] },                                              // 1 つ到達で
    two_bad:    { endings: ["bad_aoi", "bad_beni", "bad_sui", "bad_kuro"], count: 2 }, // 4 つのうち 2 つ以上で
    true_route: { endings: ["bad_aoi", "bad_beni", "bad_sui", "bad_kuro"] }            // 4 つ全部で（count 省略＝全部）
  },
  scenes: { ... }
};
```

理由：

- 対応の両端（エンディング ID とフラグ）がどちらも物語データの中身。エンディング ID は `scene.ending.id`、フラグを読むのは `requires`・`next`・`text` で、どれも `STORY` にある。`docs/ENGINE.md` §1 の境界では `WORK` は「作品の見せ方と保存キー」、`STORY` は「分岐と状態」なので、`STORY` 側が自然。
- 直前の拡張 `STORY.vars`（状態の宣言を `STORY` の最上位に置き、キー＝名前、値＝設定のオブジェクト）と同じ流儀にそろえた。点検ツールも `STORY` だけを見て完結する。

### 1-2. 書式：キー＝フラグ名、`{ endings, count }`

- **キーをフラグ名**にした（「エンディング X → フラグ F」の配列ではなく）。1 つのフラグが複数のエンディングの組合せで決まる（「4 つ全部」）ことが本題なので、フラグを主語にすると 1 件で書ける。`STORY.vars` もキーが名前。
- `count` を 1 つだけ足した。省略＝全部（AND）、`count: 1`＝どれか 1 つ（OR）、`count: n`＝n 個以上。条件の関数（`when: function (reached) {…}`）にすると自由度は上がるが、点検で「解放できるか」を確かめられなくなるので、データで書ける範囲にとどめた（§4 判断に迷った点）。
- 立つ値は `true` 固定。立ったフラグは**ふつうの `flags`** に入る（`ENGINE.md`「真偽・文字列はこれまでどおり `flags`」）。参照は `s.flags.true_route` で、新しい読み方を覚えなくてよく、点検ツールの「関数が見ているフラグを振って試す」もそのまま効く。

### 1-3. どこで写すか：`newState(reached)`

- `js/state.js` は DOM と localStorage に触らない約束なので、到達記録は `js/game.js` が読み（既存の `seenEndings()`）、**ID の配列として `newState` に渡す**。`newState` は宣言どおりにフラグを立てた状態を返す。
- `js/game.js` の変更は `startNew()` の 1 行だけ（`newState()` → `newState(seenEndings())`）。新規開始はすべて `startNew()` を通る（タイトルの「はじめから」、結末の「もう一度はじめから」、メニューの「最初から」、オートセーブが無効なときの「つづきから」）。
- `restoreState`（つづきから・ロード）と巻き戻し（控え）には手を入れていない。進行中のセーブは、その時点のフラグのまま。

### 1-4. 保存キー：足していない

- 元データは既存の `<作品 ID>-endings-v1`（到達したエンディング ID の配列）。新規開始のたびにそこから計算するので、解放済みフラグを別に保存する必要が無い。記録の消去（設定）で到達記録が消えれば、解放も自然に消える。

## 4. 判断に迷った点

1. **条件の表し方**（データ `{ endings, count }` か、関数か）。関数（`when(reached)`）なら「A と B、または C」のような条件も書けるが、点検で「解放できるか」を確かめられず、存在しないエンディング ID の誤りも拾えなくなる。依頼の例（4 つ全部）と、よくある「n 個以上」「どれか 1 つ」を `count` で書けるので、データにとどめた。複雑な条件は、解放のフラグを複数立てて `requires` の関数で組み合わせれば書ける。
2. **立つ値は `true` 固定**にした。「到達した数」を数値で渡す案（`vars` へ）もあったが、今回の用途はフラグで足り、`vars` を宣言しない作品に `vars` を出さない約束も崩さずに済む。
3. **「つづきから」でオートセーブが無効なとき**は従来どおり `startNew()` に落ちるので、解放が効く（新規開始と同じ扱い）。自然だと判断した。
4. **`effects`・`onEnter` で同じフラグを立てる**のは、「周回で解放、またはその周の中で条件を満たす」という意図的な使い方もありうるので、誤りではなく注意にした。
5. **新しい保存キーは足していない**（§1-4）。到達記録から毎回計算すれば足りるため。
6. スキルの参照資料（`.claude/skills/novel-work/references/`）は指示に明記は無かったが、新作をこのスキルで作るときに書き方と点検の文言が分かるよう、短く追記した。不要なら外して構わない。

## 5. 未解決

- **到達記録は端末（ブラウザ）ごと**。別の端末・ブラウザや、記録の消去のあとは解放されない（従来のエンディング一覧と同じ性質）。引き継ぎの仕組みは今回の範囲外。
- **タイトル画面などへの「解放された」の表示**は無い（解放の通知や、未解放のルートのヒントなど）。必要なら作品の本文（フラグを読む `text`）で出すか、別途エンジンの表示を設計する。
- 点検の「フラグなしでは届かない」は、関数を試す状態の範囲での判定（いつもの `sampleStates`）。その周の中で `effects` が立てるフラグや変数の積み重ねでだけ届く結末は、届くのに注意が出る／届かないのに出ない、ことがありうる（シミュレーションではないため）。
- 解放のフラグは `flags` に入るので、作品の中で `effects: { flags: { true_route: false } }` と書けばその周の中では消せる（エンジンは止めない）。点検の「effects・onEnter でも立てています」の注意は、値に関係なく同じフラグ名への書き込みがあれば出る（`false` を書いた場合も含む）。
