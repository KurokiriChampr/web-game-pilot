## 1. 状態変数の汎用化

### 1-1. 結論

#### (a) 考え方：置き換えずに、足す

- 状態の最上位にある `affection`（数値）・`shards`（数値）・`flags`（オブジェクト）は、名前も意味も変えない。
- 作品が自由に定義する変数は、最上位に **`vars`** を 1 つ足して、その中に入れる。
- `vars` は、**変数を 1 つ以上宣言した作品でだけ**状態とセーブに現れる。本作は宣言しないので、セーブの最上位は今と同じ 6 項目（`affection`・`flags`・`log`・`scene`・`shards`・`steps`）のまま。
- `vars` に入れるのは**数値だけ**。真偽や文字列は、これまでどおり `flags` に入れる（`flags` はもともと任意の値を持てる）。

#### (b) 宣言の形式（作品側。`js/story.js` の `STORY.vars`）

```js
var STORY = {
  start: "...",
  vars: {
    // 作品全体で 1 つの値
    gold:  { initial: 100, min: 0 },
    // 人物ごとに値を持つ。per に人物の ID を並べる
    trust: { initial: 0, min: 0, max: 10, per: ["aoi", "beni", "sui"] }
  },
  cast: { ... },
  scenes: { ... }
};
```

| 項目 | 必須 | 意味 |
| --- | --- | --- |
| （キー） | ○ | 変数名。半角英数字と `_`、先頭は英字。`set` は使えない（(c) の書き方と区別するため） |
| `initial` |  | 初期値（省略＝0） |
| `min`／`max` |  | 下限／上限（省略＝制限なし）。更新のたびにこの範囲へ収める |
| `per` |  | 人物の ID の配列。書くと「人物ごとの変数」になり、値は `{ aoi: 0, beni: 0, sui: 0 }` の形で持つ |

- `per` の ID は、立ち絵の人物 ID（manifest の `characters` のキー）にそろえることを勧める。ただし立ち絵の無い人物にも値を持たせたい作品があるので、強制はしない（点検ツールは「manifest にも cast にも無い ID」を**注意**として出す）。
- 既存の 2 つは「エンジンが最初から持っている変数」として残る。`STORY.maxAffection`・`STORY.maxShards` を書かない（または 0 の）作品では、HUD にもセーブの説明にも出ない（3.0-p4 で実装済みの挙動）。値は 0 のままセーブに入る。

#### (c) 参照と更新

**参照**（`requires`、`next` の関数、`text` の関数）：今と同じく状態 `s` を受け取り、`s.vars` をそのまま読む。

```js
requires: function (s) { return s.vars.trust.aoi >= 3 && s.vars.gold >= 30; }
next:     function (s) { return s.vars.trust.aoi > s.vars.trust.beni ? "aoi_route" : "beni_route"; }
```

**更新**（選択肢の `effects`、シーンの `onEnter`）：`effects.vars` を足す。既存の 3 項目はそのまま使える。

```js
effects: {
  affection: 1,                 // 従来どおり（加算）
  flags: { met: true },         // 従来どおり（代入）
  vars: {
    gold: -30,                  // 数値＝加算
    trust: { aoi: 2, beni: -1 },// 人物ごとの変数は、人物 ID → 数値（加算）
    // 代入したいときは { set: 値 }：  gold: { set: 0 } ／ 人物ごとなら trust: { aoi: { set: 5 } }
  }
}
```

- 数値は加算、`{ set: 値 }` は代入。適用後に `min`／`max` へ収める。
- 「人物 ID のオブジェクト」と「`{ set }`」のどちらなのかは、**宣言に `per` があるかどうか**で決まる（値の形から推測しない）。
- 宣言していない変数、`per` に無い人物への更新は、エンジンは無視してコンソールに警告を出す（進行は止めない）。点検ツールは**誤り**にする。
- 既存の挙動は変えない：`affection` は上下限なしの加算（本作は -3〜13 を取る）、`shards` は `maxShards` で頭打ち。

**シーン遷移の条件**：`choice.next` と `scene.next`（§2）の関数が `s.vars` を読む。専用の書式は足さない。

#### (d) HUD（作品側。`js/work.js` の `WORK.hud.items`）

```js
hud: {
  shards: false,
  heart: false,
  items: [
    { var: "trust", key: "aoi",  label: "アオイ", name: "アオイの信頼", style: "meter" },
    { var: "trust", key: "beni", label: "ベニ",   name: "ベニの信頼",   style: "meter" },
    { var: "gold",               label: "所持金", name: "所持金",       style: "number" }
  ]
}
```

- `style`：`meter`（横棒。`max` が要る）／`number`（数字）。欠片のような「粒」の表示は既存の `hud.shards` だけに残し、増やさない。
- `items` の DOM は**エンジンが実行時に作る**。`index.html` には要素を足さない（本作の画面が 1 画素も変わらないことと、古い画面の検出 `pageIsCurrent()` が見る id の一覧を変えないため）。
- `hud.shards`・`hud.heart` は今のまま（本作の設定は無変更で動く）。
- 並べる数の上限は設けないが、点検ツールは 5 個以上で**注意**を出す（スマホ縦の幅に収まらない見込み。実際の上限は画面で確かめて決める。§1-3）。

#### (e) 保存形式

```jsonc
// 変数を宣言した作品のセーブ（オートセーブ <id>-save-v1、スロット <id>-slots-v1 の state）
{
  "scene": "walk", "affection": 0, "shards": 0, "flags": { "met": true }, "steps": 4,
  "vars": { "gold": 70, "trust": { "aoi": 2, "beni": 0, "sui": 0 } },
  "log": [ ... ]
}
```

- キー名（`-save-v1` など 5 件）と、キーごとの入れ物の形は変えない。`vars` が増えるのは「変数を宣言した作品」だけ。
- **巻き戻し用の控え**（バックログの選択肢の行 `k: "c"` が持つ `s`）にも `vars` の写しを入れる。入れないと、選択肢へ戻ったときに変数だけが「未来の値」のまま残る。

**読み込み時の扱い**（`restoreState` に足す処理。`steps`・`log` を補っている今の処理と同じ考え方）：

| セーブの状態 | 扱い |
| --- | --- |
| `vars` が無い（変数を足す前に作ったセーブ） | 宣言の `initial` で作る |
| 宣言にあるのにセーブに無い変数・人物（作品の更新で増えた） | `initial` で補う |
| 数値でない・範囲外 | `initial` に戻す／範囲へ収める |
| セーブにあるが宣言に無い変数（作品の更新で消えた） | **消さずに残す**（古い版の画面に戻ったときに値を失わないため。エンジンは使わない） |
| 作品が変数を宣言していない | 何もしない（`vars` を作らない） |

- `isValidSave` の条件は**変えない**（`vars` を必須にしない）。足りないものは上の表で補う。
- 例外として、**変数を宣言している作品で、控えに `vars` が無い選択肢の行**には「戻る」を出さない。変数を足す前の控えからは、その時点の値が分からないため（3.0-p3 で「控えの無い旧データの行には戻るを出さない」としたのと同じ扱い）。

**現在の保存形式からの移行**：

- **本作**：移行は発生しない。変数を宣言しないので、読むデータも書くデータも今と同じ。ver 2.1 のセーブ（`tools/fixtures/v2.1-localstorage.json`）から 3.0-p4 までのセーブが、そのまま読める。
- **別作品**：新しい形式で最初から始まる。途中の版で変数を足しても、上の表の補完で既存セーブは読める。

#### (f) エンジン側の置き場所

状態の計算（`newState`・`applyEffects`・`restoreState`・`isValidSave`・`snapshotOf`・`visibleChoices`）は、いま `js/game.js` の内側にあり、ブラウザを動かさないと検査できない。**新しいファイル `js/state.js`（`GameState`）へ切り出す**ことを提案する。`js/stage.js` と同じく画面に触れない計算だけを置き、Node からも読めるようにする（`tools/lib/load-work.js` は `assets.js`・`game.js` 以外を実行するので、そのまま読み込まれる）。

- 得るもの：変数の加算・範囲・補完・控えの写しを、`tools/test-stage.js` と同じ流儀で大量に単体検査できる。`tools/validate-story.js` が、エンジンと同じ関数で effects を適用して点検できる。
- 代償：`index.html` の `<script>` が 1 つ増える（`?v=` が 7 → 8 か所）。`tools/e2e-p3.js` の `?v=` の数の期待値と、`tools/e2e-p4.js`「0. 境界」の対象ファイルの一覧を書き換える必要がある。
- 代案：切り出さずに `js/stage.js` へ入れる（読み込みは増えないが、「舞台の計算」という役割がぼやける）。

### 1-2. 根拠

1. **本作の `js/story.js` が `s.affection`・`s.shards`・`s.flags.xxx` を直接読んでいる**（`next`・`requires`・`text` の関数で 30 か所以上）。本作のデータを変えない条件のもとでは、この 3 つの名前と位置は動かせない。「全部を `vars` に入れて、古い名前は別名にする」案は、別名を成り立たせる仕掛け（getter）が JSON の複製（`restoreState`、控えの作成）で消えるので採らなかった。
2. **既存の検査が、セーブの最上位の形を固定している**。`tools/e2e.js` 367〜368 行と `tools/e2e-p3.js` 424・1397 行が、キーの一覧が `affection`・`flags`・`log`・`scene`・`shards`・`steps` と一致することを確かめている。「宣言した作品でだけ `vars` が現れる」形なら、この検査は書き換えずに通る見込み。
3. **古い版の画面との混在**。本作は、利用者の端末に古い版の画面が残ることを前提にした仕組み（`handleStalePage`）を持つ。古い版の `isValidSave` は `affection`・`shards` が数値であることを求めるので、この 2 つをセーブから消すと、古い画面で「セーブが無い」扱いになる。残しておけば、古い版は `vars` を無視して読める（`log` の `who` や控え `s` を足したときと同じやり方）。
4. **人物ごとの値を「変数名 → 人物 → 値」の入れ子にした理由**。逆（人物 → 変数）や、`trust_aoi` のような名前の連結に比べて、宣言 1 つに上下限と初期値を 1 回書けば済み、`s.vars.trust.aoi` と読める。点検ツールが関数の中の参照（`.vars.trust.aoi`）を文字列から拾うのも、今のフラグの拾い方（`.flags.xxx`）と同じ方法でできる。
5. **宣言を `STORY` に置いた理由**。変数は分岐の論理の一部で、`next`・`requires` と同じファイルにあるほうが読み書きしやすい。今も上限値（`maxAffection`・`maxShards`）は `STORY`、呼び名（`hud`）は `WORK` にあり、その分け方を引き継いだ。
6. **数値だけにした理由**。真偽と文字列は `flags` で足りており（`applyEffects` は `flags` に任意の値を代入する）、型を増やすと、HUD・点検・補完のそれぞれに型ごとの分岐が要る。
7. **宣言なしの自由な読み書きを認めなかった理由**。宣言があるから、古いセーブの補完、範囲の保証、点検（綴り間違いの検出）ができる。長編では変数名の綴り間違いが見つけにくい不具合になる。

### 1-4. 残る未決事項

1. **宣言の置き場所**（`STORY.vars` か `WORK.vars` か）。提案は `STORY`。
2. **`js/state.js` を切り出すか**（§1-1 (f)）。提案は切り出す。
3. **HUD に並べられる数と、スマホ縦での見せ方**。3 人ぶんの横棒＋数字 1 つが 360px 幅に収まるかは、画面を作って測らないと決められない。収まらない場合の案：HUD には 2〜3 個だけ出し、残りはメニューの中の一覧に出す。
4. **値が変わったときの知らせ方**。今は欠片が通知、好感度がゲージの動き。変数ごとに「知らせる／知らせない」を選べるようにするか（隠しパラメータにしたい作品がある）。提案は「HUD に出しているものだけゲージを動かす、通知は出さない」。
5. **セーブの説明に変数を出すか**（今は欠片だけ出している）。提案は出さない。
6. **条件を関数でなくデータで書く書式**（例：`requires: { vars: { trust: { aoi: { gte: 3 } } } }`）は今回入れていない。入れれば点検ツールが境界の値を正確に試せ、スキルで物語を書かせるときの誤りも減る。一方で書式が増え、関数との二本立てになる。別作品を 1 本作ってから要否を決めたい。
7. 点検ツールの限界は今と同じ：変数を 1 つずつ振って試すので、**複数の変数の組合せでだけ起きる問題は見つけられない**。
8. `verify-text.js` を別作品で使える形にする件（汎用化報告書 §4-2 の 8）は、この設計の範囲外。変数が増えると全組合せの照合はさらに回らなくなるので、別作品用の本文の固定化は別の方法（代表的な道筋の記録など）が要る。

**迷った点**：

- 「新しい作品でも `affection`・`shards` が 0 のままセーブに入り続ける」のは、きれいではない。古い版との互換と既存の検査を優先して残した。別作品だけを考えるなら不要な項目である。
- `flags` を `vars` に統合する案も考えたが、本作のデータが `s.flags` を読んでいるので採れなかった。結果として「真偽は `flags`、数値は `vars`」の二本立てになる。
- 加算と代入の書き分け（数値＝加算、`{ set }`＝代入）は、`affection` の今の意味（加算）に合わせた。「数値を書いたら代入だと思った」という取り違えは起こりうる。点検ツールでは検出できない。

## 2. 選択肢なしのシーン遷移 `scene.next`

### 2-1. 結論

#### (a) 書式

```js
scenes: {
  prologue_1: {
    title: "雨の朝",
    text: [ "……", "……" ],
    next: "prologue_2"                       // シーン ID
  },
  prologue_2: {
    title: "駅まで",
    text: [ "……" ],
    next: function (s) { return s.flags.late ? "run" : "walk"; }   // 状態を受け取って ID を返す関数も可
  }
}
```

- `next` は「シーン ID」または「状態を受け取って ID を返す関数」。選択肢の `next` と同じ形。
- 遷移のときに状態を変えたいときは、**行き先のシーンの `onEnter`** を使う（既存の仕組み。`next` 専用の effects は足さない）。

#### (b) 動き

1. 最終ページを表示し終えた時点で、今と同じく「シーンを最後まで読んだ」と記録する。送りの印（▼）を出して**待つ**（自動では切り替えない）。
2. もう一度送る（タップ／Enter）と、行き先を決めて次のシーンへ入る。
3. 入り方は選択肢を選んだときと同じ：`scene` を書き換え、`steps` を 1 増やし、行き先の `onEnter` を適用し、バックログにシーンの行を足し、オートセーブして、最初のページから表示する。

#### (c) `choices` との併用・排他のルール

| シーンの書き方 | 動き | 点検ツール |
| --- | --- | --- |
| `ending` あり | 結末。`choices`・`next` は使わない（今と同じ） | `next` があれば**注意** |
| `choices` だけ | 今と同じ | 全部の選択肢に `requires` があるなら**注意**（全部隠れると進めない） |
| `next` だけ | 一本道 | 行き先が無ければ**誤り** |
| `choices` と `next` の両方 | **見える選択肢が 1 つ以上あれば選択肢。0 個のときだけ `next`** | 誤りにしない |
| どれも無い | 進めない | **誤り**（今の「結末でないのに選択肢がありません」を「選択肢も next もありません」に変える） |

- 「選択肢を出したうえで、時間切れで `next` へ進む」のような併用はしない。
- `next` だけで輪になっていて抜けられない並び（A → B → A）は、点検ツールが**誤り**にする（行き先が関数で、状態しだいで抜けられる場合は**注意**）。オートのまま回り続けるのを防ぐため。

#### (d) 既読・バックログ・章立てとの関係

| 観点 | 扱い |
| --- | --- |
| 既読 | **形式は変えない**。ページの記録（`シーン#指紋`）とシーンの記録（シーン ID）は今と同じ時点で付く。選択肢の記録（`シーン>指紋`）は付かない（選んでいないため）。「読んだシーン n / N」の数え方も同じ |
| 既読スキップ | 今と同じくシーンの中だけ。既読が続けば最終ページで止まり、1 回送ると次のシーンへ進む。シーンをまたいで飛び続けることはしない（§2-4 の 2） |
| オート | 最終ページでも、いつもの待ち時間のあとで次のシーンへ進む（今は最終ページで止まる。選択肢を自動で選ばないため）。選択肢と結末では今と同じく止まる |
| バックログ | 行の種類は増やさない。シーンの行（`k: "s"`）が続けて並ぶだけで、選択肢の行（`k: "c"`）は入らない。行数・ページ数の上限は今のまま働く |
| 巻き戻し | 控えを持つのは選択肢の行だけなので、「戻る」「直前の選択へ戻る」は、**いちばん近い選択肢**まで戻る（途中の一本道のシーンをまとめて戻る）。一本道の途中へは戻れない |
| 幕の数（`steps`） | `next` で進んだときも 1 増やす。`steps` は「シーンを移った回数」のまま |
| 章 | 章の判定はシーンごと（`chapterOf`）なので、`next` で章をまたげば、幕の呼び名が次の章の題名に変わる。追加の仕組みは要らない |
| 舞台 | シーンに入るたびに `stage` から組み直す（今と同じ）。前のシーンの立ち絵を続けて出したいときは、次のシーンの `stage.show` に書く |

#### (e) 保存／再開時の扱い

- **セーブに足す項目は無い。** オートセーブは今と同じく「シーンに入ったとき」。再開は、そのシーンの最初のページから（ページ位置は今も保存していない）。
- 「最終ページで送りを待っている」状態は保存しない。再読み込みすると、そのシーンの頭に戻る。
- 一本道のシーンでも手動セーブはできる（結末以外ならどこでも。今と同じ）。
- 古い版の画面が `next` を使う作品のセーブを読むと、選択肢の無いシーンで進めなくなる。ただし `next` を使うのは新しい作品だけで、その作品に古い版の画面は存在しない。本作は `next` を使わないので関係しない。

#### (f) エンジンの変更箇所（参考。実装はしていない）

- `endOfScene()`：結末 → 見える選択肢があれば選択肢 → `next` があれば「送り待ち」の順に分ける。
- `advance()`：送り待ちのときに送られたら、次のシーンへ入る。
- `choose()` の後半（シーンへ入る処理）を共通の関数にして、`next` からも使う。
- `scheduleAuto()`：送り待ちのときも時間で進める。
- `tools/validate-story.js`：`SCENE_KEYS` に `next`、(c) の表のルール、到達できるシーンの計算に `next` の行き先を足す。

### 2-2. 根拠

1. **今のエンジンには「見える選択肢が 0 個」のときの行き場が無い**。`endOfScene()` は結末でなければ `showChoices()` を呼び、`requires` で全部が隠れると空の選択肢の画面で止まる。本作では起きない（どのシーンにも無条件の選択肢がある）が、長編では起きうる。併用を「選択肢が優先、0 個なら `next`」にすれば、`next` がそのまま保険になる。
2. **最終ページで待つ理由**。今のコードは、最終ページの文字送りが終わった瞬間に選択肢を出す。同じ時点でシーンを切り替えると、最後の 1 ページを読む時間が無くなる。
3. **保存形式に触れずに済む理由**。再開の単位がもともとシーンで、バックログは「シーンの行」と「選択肢の行」の並びを前提にしていない（`trimLog`・`rewindTo`・`openLog` は行の種類ごとに処理している）。巻き戻し `rewindTo(index)` は「その行より前のログを残し、控えの状態へ戻す」だけなので、間に一本道のシーンが挟まっていても同じ処理で正しく戻る。
4. **`steps` を増やす理由**。`steps` は今「選択肢を選んだ回数」だが、本作ではそれが「シーンを移った回数」と必ず一致する。`next` で増やさないと、一本道が続くあいだ「第 3 幕」のまま題名だけが変わる。増やす定義なら、本作の数え方は変わらない。
5. **`next` 専用の effects を足さない理由**。`onEnter` で同じことができ、項目を増やすと点検と検査の対象が増える。
6. 汎用化報告書 §4-2 の 2 が挙げた波及先（バックログ・巻き戻し・オート・スキップ・幕の数え方）は、上のとおりすべて既存の仕組みの範囲で扱える。新しい保存項目や行の種類は要らなかった。

### 2-3. テストへの影響

| 検査 | 影響の見込み |

| `tools/test-stage.js` | 既存はそのまま（本作の点検結果 20／20／4／1 は変わらない）。**追加**：点検ツールが (c) の表の各行を拾うこと、輪の検出、`next` の行き先が到達できるシーンに数えられること |

### 2-4. 残る未決事項

1. **`choices` と `next` の併用を認めるか**。提案は「併用可・選択肢優先」。排他にする（両方あれば誤り）ほうが規則は単純で、検査も 1 節減る。その場合、「全部の選択肢が隠れると止まる」穴は、点検ツールの注意でしか防げない。
2. **既読スキップをシーンをまたいで続けるか**。提案はまたがない（今の「シーンの中だけ」を保つ）。既読の一本道が長く続く長編では、スキップと送りを交互に押すことになる。またぐ形にすると、止まる条件（未読・選択肢・結末）の判定がシーンの切り替えを挟むようになり、手が入る範囲が広がる。別作品で実際に読んでみてから決めたい。
3. **一本道で進んだときのシーン名の帯（バナー）**。今はシーンに入るたびに「第 n 幕／題名」の帯が出る。短いシーンが一本道で続くと、帯が頻繁に出てうるさい可能性がある。シーンごとに帯を出さない指定を足すかどうかは、画面を見てから決めたい。
4. **`steps` の定義**（提案は `next` でも増やす）。「選んだ回数」を別に数えたい作品があるかどうか。
5. **オートが一本道を通り抜けること**の是非。3.0-p3 の報告で未解決だった「オートの止まり方の意向確認」と合わせて決める必要がある。
6. 連打への備え：選択肢には誤タップ防止の待ち時間（450 ms）があるが、`next` の送りには設けない案にした（分岐を選ぶわけではないため）。連打でシーンを読み飛ばす心配があるなら、シーンの切り替え直後だけ短い待ち時間を入れる。

**迷った点**：

- 併用のルールは、単純さ（排他）と、止まる穴をふさぐこと（併用）のどちらを取るかで迷った。穴が今のエンジンに実際にあることを重く見て、併用にした。
- 巻き戻しが「一本道の途中」へ戻れないことは、長い一本道のあとで結末に着いたときに不便になりうる。一本道のシーンにも控えを持たせる案は、セーブが太る（控えの上限 40 を一本道が食う）ので採らなかった。

## 3. Claude Code スキル化

### 3-1. 結論

#### (a) 段階と置き場所

| 段階 | 形 | 中身 |
| --- | --- | --- |
| **第 1 段階（提案）** | このリポジトリの中のプロジェクトスキル `.claude/skills/novel-work/` | エンジンは複製しない。スキルは、リポジトリにあるエンジンを使って新しい作品のフォルダを作る |
| 第 2 段階 | リポジトリの外でも使える形（プラグイン） | エンジンの写しを同梱する。写しは手で保守せず、スクリプトでリポジトリから作る |

第 1 段階の作品の置き場所は `works/<作品 ID>/`（作品が差し替えるファイルだけを持つ）。確認は、3.0-p4 で作った重ね合わせの仕組みをそのまま使う：

```sh
node tools/validate-story.js --work works/<作品 ID>
node tools/preview-server.js --work works/<作品 ID> --placeholders
```

公開するときは、エンジンと作品を 1 つのフォルダへまとめるスクリプト（スキルに同梱）を使う。

#### (b) 構成案

```
.claude/skills/novel-work/
├── SKILL.md                    手順の本体（200 行前後に収める）
├── references/
│   ├── story-format.md         物語データの書式（シーン・ページ・舞台指示・選択肢・next・変数・章）
│   ├── work-config.md          js/work.js の項目、css/work.css の配色
│   ├── assets.md               素材の置き方と manifest（docs/ASSETS.md の要点）
│   ├── checks.md               validate-story の誤り・注意の一覧と、直し方
│   └── pitfalls.md             守ること（作品 ID を公開後に変えない、シーン ID に # と > を使わない、同じ本文のページ、押し出し ほか）
├── templates/
│   ├── minimal/                最小の作品（1 人・3 シーン・結末 1）
│   │   ├── js/work.js
│   │   ├── js/story.js
│   │   ├── css/work.css
│   │   └── assets/manifest.json
│   └── chapter.js              章のファイルのひな形（GameStage.addChapter）
└── scripts/
    ├── new-work.js             works/<ID>/ をひな形から作る（ID の書式と重複を確かめる）
    └── build-work.js           エンジン＋作品を 1 つのフォルダへまとめる（公開用。index.html の題名・説明・版・章の <script> を書き込む）
```

#### (c) SKILL.md に書くこと

- **冒頭の定義**（`name`・`description`）：何をするスキルか、いつ使うか。例：「このリポジトリのノベルゲームエンジンで新しい作品を作る・書き足す・点検する。『新しいノベルゲームを作りたい』『シーンを足して』『物語データを点検して』のときに使う」。
- **最初に確かめること**：作品 ID、題名、登場人物、結末の数、変数を使うか、素材があるか（無ければ仮の画像で進める）。
- **手順**（番号付き）：
  1. `scripts/new-work.js` で作品のフォルダを作る
  2. `js/work.js` を書く（`references/work-config.md`）
  3. 物語データを書く（`references/story-format.md`）。長編なら章に分ける
  4. `assets/manifest.json` と素材（`references/assets.md`）
  5. `node tools/validate-story.js --work …` を**誤り 0 件になるまで**回す。注意は 1 件ずつ意図どおりか確かめる（`references/checks.md`）
  6. `node tools/preview-server.js --work … --placeholders` で画面を確かめる
  7. 公開する場合は `scripts/build-work.js`
- **守ること**（短い一覧。理由を添える。詳細は `references/pitfalls.md`）。
- **してはいけないこと**：エンジンのファイル（`js/game.js` など）と本作のデータ（`js/story.js`、`assets/`）を書き換えない。エンジンに足りない機能が要るときは、作業を止めて依頼者に知らせる。
- 参照資料は、必要になった段で読むよう案内する（最初から全部は読ませない）。

#### (d) 収録範囲

| 範囲 | 含めるか | 理由 |
| --- | --- | --- |
| エンジンの使い方（境界、作品設定、プレビュー） | **含める** | これが無いと作品を始められない |
| story の書き方（書式、舞台指示、3 人表示、章、変数、`next`） | **含める**（スキルの中心） | 作業の大半はここ |
| `validate-story` の回し方と、結果の読み方・直し方 | **含める** | スキルが自分の出力を確かめる唯一の機械的な手段 |
| 素材の置き方（フォルダ、manifest、仮の画像での進め方） | **含める** | manifest の不整合は点検で誤りになる。素材が無くても進められることが重要 |
| 素材そのものの制作（絵・音の生成、画風の指定） | 含めない | 別の作業。`docs/ASSETS.md` にある本作向けの指示は、本作に固有 |
| 物語の内容の作り方（プロット、文体） | 含めない | 作品ごとに依頼者が決めること。スキルは書式と点検までを受け持つ |
| エンジンの改造、既存の検査（`e2e*.js`・`verify-text.js`）の回し方 | 含めない | エンジンの開発は別の作業。作品づくりでは回さない（本作が前提の検査） |
| 公開（まとめるスクリプトまで） | まとめる所まで含める | GitHub Pages への配置そのものは、リポジトリの設定によるので手順に書かない |

#### (e) 作り方の手順案

1. **前提をそろえる**：§1・§2 の採否を決める（採るなら実装を先に済ませる。書式が変わるとスキルの参照資料を書き直すことになる）。
2. **実際に 1 本、手で作ってみる**：`tools/fixtures/trio/` を写して最小の作品を作り、汎用化報告書 §3 の手順（9 項目）でつまずく所を書き留める。それが `pitfalls.md` と `SKILL.md` の手順の材料になる。
3. **ひな形とスクリプトを作る**：`templates/minimal/`、`new-work.js`、`build-work.js`。ひな形は点検で誤り 0・注意 0 になる状態にしておく。
4. **参照資料を書く**：`docs/ENGINE.md`・`docs/ASSETS.md`・`js/story.js` 冒頭の説明を、作品を作る人の視点で書き直す（写しを 2 か所で保守しないよう、スキル側を正とし、`docs/ENGINE.md` からはスキルの資料を指す形を勧める）。
5. **SKILL.md を書く**。
6. **試す**：何も知らない状態の新しいセッションで「このエンジンで 3 人の短い話を作って」などの依頼を 3〜5 通り出し、スキルが使われるか、点検が誤り 0 になるか、エンジンのファイルに触れていないか（`git status` で確かめる）を見る。つまずいた所を資料に戻す。
7. **検査に組み込む**：ひな形を `tools/validate-story.js --work` で点検する確認を `tools/test-stage.js` に足す（エンジンの変更でひな形が壊れたら気づけるように）。
8. 第 2 段階（外へ配る形）は、第 1 段階で作品を 1 本作り終えてから。

### 3-2. 根拠

1. **重ね合わせの仕組みがすでにある**。`tools/preview-server.js --work` と `tools/validate-story.js --work` は、作品のフォルダにあるファイルを優先し、無いものをエンジンから読む。`tools/fixtures/trio/` は 3 ファイルだけで別作品として動いている。第 1 段階のスキルは、この仕組みに手順とひな形を足すだけで成り立つ。
2. **エンジンを複製しない理由**。エンジンはまだ変わる（§1・§2、汎用化報告書 §4-2 の見送り 13 件）。写しをスキルに入れると、直すたびに 2 か所を合わせる必要があり、古い写しで作った作品が出る。
3. **汎用化報告書 §3 が「足りないもの」として挙げた 3 点**への対応：
   - 境界の残り（§2 の 1〜6）：1 は本設計の §1。3（タイトルの紋章）と 6（`index.html` の題名）は、`build-work.js` が書き込む所と、手で直す所を `pitfalls.md` に明記して当面しのぐ。
   - フォルダが分かれていない：`works/<ID>/` に作品だけを置くことで、エンジンのファイルを動かさずに分けられる（見送り 3 の「`engine/`・`work/` に分ける」を実施しなくてよい）。
   - 別作品用の画面検査が無い：スキルの範囲では `validate-story` と目視（プレビュー）まで。画面の自動検査は第 2 段階以降の課題として残る。
4. **SKILL.md を短くし、参照資料を分ける理由**。スキルの本文は使われるたびに読み込まれる。書式の全部を本文に入れると長くなり、手順が埋もれる。書式は、物語を書く段になって読めば足りる。
5. **`validate-story` を手順の関門にする理由**。行き先の無い選択肢、`cast` に無い話者、manifest に無い表情は、画面を動かさないと気づけない誤りで、長編ほど見落とす。点検ツールは数秒で全シーンを見る。

### 3-3. 残る未決事項

1. **スキルの置き場所**。このリポジトリの中（提案）か、最初から外へ配る形か。前者はこのリポジトリを開いたセッションでしか使えない。
2. **作品の置き場所**。`works/<ID>/` をこのリポジトリに置くと、エンジンと複数の作品が 1 つのリポジトリに同居する。作品ごとに別のリポジトリにしたい場合は、第 2 段階の形が要る。
3. **本作の扱い**。本作のデータはリポジトリの直下（`js/story.js` など）にあり、`works/` には入らない。当面はそのまま（本作のファイルを動かすと、既存の検査 7 本と保存キー・公開 URL の確認が要る）。「直下が本作、`works/` がそれ以外」という非対称が残る。
4. **`build-work.js` が `index.html` をどこまで書き換えるか**。題名・説明・版・章の `<script>` は機械的に入れられる。タイトル画面の紋章（文字盤の針）は本作固有の絵で、外すか差し替えるかは作品ごとの判断になる（汎用化報告書 §4-2 の 5 が未実施のため）。
5. **版の付け方**。作品の版とエンジンの版が 1 つの値を共有している（同 §4-2 の 9）。作品を複数作ると、エンジンを直すたびに各作品の版をどう上げるかが問題になる。
6. **スキルの名前と、使われるきっかけの文言**（`description`）。実際に試して調整する（手順 6）。
7. **素材の生成をどこまで扱うか**。今回は範囲外にした。仮の画像で最後まで作れることを優先した。
8. スキルで作った作品の**実機確認**は、スキルではできない。汎用化報告書 §7 の 1・2（実機未確認、3 人表示を実素材で確かめていない）は、スキル化しても残る。

**迷った点**：

- 「エンジンの使い方から素材の置き方まで」を 1 つのスキルにまとめるか、物語を書くスキルと点検のスキルに分けるかで迷った。作品づくりは 1 本の流れで、途中で何度も点検に戻るので、1 つにまとめる案にした。参照資料を分けることで、本文の長さは抑える。
- 公開用にまとめるスクリプト（`build-work.js`）は、エンジンに「作品を重ねて配信する」仕組みが無いことの埋め合わせで、本来はエンジン側の課題（見送り 3）である。スキルの中に置くと、エンジンの構成の知識がスキル側にも入り込む。`tools/` に置く案もある。

## 4. 全体を通して

### 4-1. 不変条件の確認

| 条件 | この設計での扱い |

### 4-2. 実装する場合の順番と規模の見込み

| 順 | 内容 | 規模 | 理由 |

### 4-3. この設計で確かめていないこと

- **コードを動かしていない。** 「変更不要の見込み」と書いた検査は、該当箇所を読んだ上での判断で、実行していない。とくに `tools/e2e-p4.js` の画面 164 枚の一致は、HUD と進行の関数に手を入れたあとで実際に回さないと保証できない。

- HUD に複数のゲージを並べたときの見た目、一本道でのバナーの出方は、画面を作っていないので判断していない。
- スキルの構成は Claude Code の一般的な作り（`SKILL.md`＋同梱ファイル）に沿った案で、実際に使われるか・手順どおりに動くかは試していない。
